Comparison:
  - OLTP  : 93.219 ms   (sql/analysis/q4_revenue.sql)
  - STAR  : 42.473 ms
  - Improvement: 2.2x faster
  - Parity: proven identical, both EXCEPT directions, 192 rows
            (tests/13_parity_q4.sql)

Why it is faster:
  `billing` does not appear in this query at all. total_allowed_amount and
  claim_count are already columns on the fact, so an entire table - and the
  longest join chain in the lab - drops out. Four tables become fact plus two
  dimensions, and the Denied-claim filter was applied once at load time rather
  than on 61,598 rows per run.

  dim_specialty is joined after the aggregate, so the GROUP BY runs on a 4-byte
  surrogate key instead of a VARCHAR(100), and the month comes from a stored
  column rather than a per-row date_trunc().

  Only 2.2x, and the reason is worth stating: Q4 was already the mildest case.
  Its aggregation was a HashAggregate even in the OLTP schema, because SUM and
  COUNT run with a running accumulator and need no sort. There was no sort to
  eliminate, unlike Q1 - so what is left is the join chain and the date
  derivation. Removing a whole table from a query that was already fast returns
  proportionally less than removing a self-join from one that was not.

Two things that make this an exact translation rather than a near-enough one:

  1. claim_count. Q4's COUNT(*) counts BILLING ROWS, not encounters. The fact is
     at encounter grain, so the equivalent is SUM(f.claim_count) - never
     COUNT(*) over fact rows, which would count encounters and be wrong by the
     number of multi-claim encounters. SUM(smallint) returns bigint, matching
     COUNT(*), so the parity EXCEPT needs no cast.

  2. WHERE f.claim_count > 0. Q4 is anchored FROM billing, so a (month,
     specialty) combination with no payable claim produces NO ROW. The fact holds
     a row for every encounter, billed or not, so without this predicate the star
     emits that group with total_allowed = 0. The SUMS are identical either way -
     unbilled rows carry 0, the additive identity - so what this predicate
     controls is group EXISTENCE and nothing else. That is exactly why it is easy
     to omit and quietly return 193 rows instead of 192, with every total
     correct. tests/13 asserts the filtered group count equals the OLTP row count
     so this cannot regress unnoticed.

  The Denied filter lives in the ETL's billing CTE and in Q4's WHERE clause, and
  the two must match. If they ever diverge the parity test fails - and the ETL is
  what is wrong, not the test. tests/07 carries a negative control proving the
  filter is genuinely applied rather than accidentally a no-op on both sides.
