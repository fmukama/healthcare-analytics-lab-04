 DESIGN DECISIONS - Healthcare OLTP to Star Schema
 Part 3.1
*******************************************************

All figures come from the loaded dataset (70,004 encounters) and the EXPLAIN
ANALYZE output in query_analysis.txt. Nothing here is estimated.


------------------------------------------------------------------------------
DECISION 1: Fact table grain
------------------------------------------------------------------------------
  Choice   : Option A - one row per encounter
  Rejected : B (per diagnosis), C (per procedure)

      A  one row per encounter      70,004 rows
      B  one row per diagnosis     175,024 rows
      C  one row per procedure     104,955 rows

  B breaks the money. At diagnosis grain each encounter's billing repeats once per
  diagnosis, so SUM(total_allowed_amount) inflates by the mean diagnosis count -
  about 2.5x, turning a true $139.6M into roughly $349M. Nothing errors; the
  numbers are quietly wrong. This is the fan trap.

  C breaks it worse. 11,725 encounters (16.7%) have no procedure, so at procedure
  grain they vanish entirely, taking their revenue and readmissions with them.
  Silent data loss, not just double counting.

  A matches the questions. All four aggregate at encounter level or above, so there
  is no de-duplication at query time and money stays additive - the property that
  makes a fact table safe to hand to someone else.

  Cost: no diagnosis or procedure code can live on the fact row. That detail moves
  to bridges, and Q2 keeps a many-to-many join the other three shed. This grain
  also cannot answer "average revenue per diagnosis" - that is a different fact.


------------------------------------------------------------------------------
DECISION 2: Dimension tables
------------------------------------------------------------------------------
  Seven dimensions. Surrogate *_key on each, source *_id kept for traceability.

  dim_date            date_key (YYYYMMDD), year, quarter, month, month_name,
                      year_month, day_of_month, day_of_week, is_weekend
  dim_patient         patient_id, mrn, names, date_of_birth, gender
  dim_specialty       specialty_id, specialty_name, specialty_code
  dim_department      department_id, department_name, floor, capacity
  dim_provider        provider_id, names, credential, plus denormalized
                      specialty_key/name and department_key/name
  dim_encounter_type  type_name, is_inpatient, is_emergency
  dim_diagnosis       icd10_code + description   } reached through bridges,
  dim_procedure       cpt_code + description     } never from the fact

  Four choices worth naming:

  Smart date key (20240510, not a sequence) - readable in a plan, sorts naturally.
  year_month is stored, so GROUP BY reads a column instead of calling date_trunc()
  70,004 times.

  Dates role-play. The fact holds admit_date_key and discharge_date_key, the
  procedures bridge holds procedure_date_key, all pointing at the same dim_date.

  No age_group in dim_patient. Age drifts, so an age band in a dimension silently
  rewrites history on reload and last year's report stops reproducing.
  date_of_birth stays here; age_at_encounter goes on the fact, correct forever.

  specialty_key sits directly on the fact. This is what collapses Q1 and Q4: in
  3NF the database walks encounters -> providers -> specialties for every row; on
  the fact it is one hop and dim_provider is never touched. dim_provider is
  likewise flattened, not snowflaked - snowflaking rebuilds the join chain this
  exercise exists to remove.

  Cost: real duplication. specialty_name lives in three places and every ETL run
  must keep them consistent. Traded for removing a join from the two most
  frequently run queries.


------------------------------------------------------------------------------
DECISION 3: Pre-aggregated metrics
------------------------------------------------------------------------------
  Computed once at load time, stored on the fact row:

      diagnosis_count           removes a join to a 175,024-row junction
      procedure_count           removes a join to a 104,955-row junction
      claim_count               separates "unbilled" from "allowed zero"
      total_claim_amount        billing drops out of Q4 entirely
      total_allowed_amount      the measure Q4 asks for
      length_of_stay_hours      computed once instead of per query
      age_at_encounter          correct forever, unlike an age band
      is_inpatient              integer flag beats a string comparison
      is_readmit_30d            removes Q3's self-join
      days_to_next_encounter    keeps the 30-day threshold auditable
      encounter_count           always 1; keeps SUM() valid at any roll-up

  is_readmit_30d is the one that matters. Q3 costs 8,701ms and 8,939,200 buffer
  hits because the correlated subquery re-scans encounters once per index stay.
  Computing the flag during ETL turns the question into a GROUP BY over a boolean -
  the self-join is not optimised, it stops existing.

  The principle: pre-aggregation moves cost from query time, paid by every analyst
  on every run, to load time, paid once, off-hours.

  Cost: the fact holds derived data, which goes stale when definitions change. If
  readmission moves to 45 days the column must be reloaded - no query edit fixes
  it. Incremental loads are harder than they look: the flag depends on the NEXT
  encounter, so already-loaded rows must be recomputed at least 30 days back.


------------------------------------------------------------------------------
DECISION 4: Bridge tables
------------------------------------------------------------------------------
  Choice   : Yes - bridge_encounter_diagnoses and bridge_encounter_procedures
  Rejected : repeating columns on the fact; changing the grain

  Flattening into diagnosis_1 ... diagnosis_N is a repeating group. It breaks the
  first time a patient has N+1 diagnoses, and "find every encounter with code I10"
  becomes a scan of every column. Changing the grain instead is Decision 1 option
  B, already rejected.

  The bridge keeps full many-to-many detail, keeps the fact additive, and confines
  the many-to-many join to the one query that needs code-level detail. Q1, Q3 and
  Q4 never touch these tables. That containment is the win, not the join itself.

  The two bridges are keyed differently, on purpose:

    diagnoses   PK (encounter_sk, diagnosis_key). The same ICD-10 code twice in one
                encounter is a data entry error, so collapsing it is correct.

    procedures  Surrogate bridge_sk with the source encounter_procedure_id as a
                UNIQUE natural key. The same CPT code genuinely can occur twice -
                two chest X-rays are two billable events. A composite key would let
                ON CONFLICT DO NOTHING swallow the second, and procedure_count
                would stop matching the bridge.

  Cost: Q2 stays a many-to-many join. It gets faster - narrower tables, integer
  keys, no hop through encounters - but it is the one query that does not become
  trivial. In production the fix is a pre-built summary table, buying speed at the
  price of answering one question instead of any. Adding allocation_factor
  (1.0 / diagnosis_count) would let revenue split across diagnoses without double
  counting - Kimball's weighted bridge - but no query here needs it.


------------------------------------------------------------------------------
SUPPORTING DECISIONS
------------------------------------------------------------------------------
  Engine: PostgreSQL 16 over MySQL 8. EXPLAIN (ANALYZE, BUFFERS) reports actual
  rows and buffers per plan node, and EXCEPT proves a rewrite returns the same
  rows. The buffers mattered more than expected - Q3's bottleneck is invisible in
  the timing but obvious at 8,939,200 buffer hits.

  Data volume: 70,000 encounters across 7,000 patients, generated. The brief's 4
  sample rows run in under a millisecond and contain zero readmissions, so Q3
  returns 0% whether the query is right or wrong. The 1:10 patient-to-encounter
  ratio is not cosmetic - repeat visits are the only reason a readmission exists.
  600k was rejected: a full run becomes a ~25 minute job. Below ~30k, Q1 and Q4
  fall into run-to-run jitter.

  Department on the fact is the encounter's, not the provider's. They disagree for
  9.3% of encounters and answer different questions: "where was care delivered"
  versus "which unit does this clinician report to".

  Unbilled is 0, not NULL - additive measures, and 0 is the truthful identity;
  NULL would make AVG() skip the row. claim_count is the discriminator: 13,430
  rows have claim_count = 0, being 8,406 never billed plus 5,024 wholly denied.

  Denied claims excluded from revenue - 5,024 of 61,598. Counting them overstates
  revenue at $151.8M against a truthful $139.6M. Pending is kept, since
  allowed_amount is contractually agreed. Nobody specified this; the point is that
  it is decided and written down.

  Revenue is dated by encounter_date, not claim_date, so it lines up with when care
  happened rather than when paperwork was filed.

  Foreign keys are never NULL; unresolved lookups map to -1. A NULL FK drops the
  row from every inner join, making bad data invisible. A -1 Unknown member keeps
  the row and makes the problem countable.

  dim_encounter_type is a curated list, not SELECT DISTINCT - deriving reference
  data from facts means 'ER' vanishes in any period with no ER visits.

  SCD Type 1 on all dimensions. Type 2 is sketched in the DDL but not built, since
  no listed question asks "as at the time". Cost: a patient who changes surname
  reprints under the new name in last year's report. Type 2 would also break the Q1
  parity test - one patient would hold several patient_keys and
  COUNT(DISTINCT patient_key) would inflate.

  Indexes are required by the brief and useful, but they are not why the star
  schema is faster. Q1's OLTP plan already ignores idx_encounter_date and scans
  sequentially: an index helps you find a few rows, and these queries read all of
  them. The speedup comes from fewer joins and pre-computation.


------------------------------------------------------------------------------
KNOWN LIMITATIONS
------------------------------------------------------------------------------
  The generator assigns providers at random with no specialty-linked readmission
  risk, so all eight specialties land between 30% and 34%. Q3's ranking is noise.
  The ~32% baseline is itself an artifact of uniform arrivals: ten visits over 730
  days gives a ~73-day mean gap, so 1 - e^(-30/73) = 34%, which is what was
  measured. Real hospitals run 15-20%. The query is correct; the data has no signal.

  The volume generator is deliberately not idempotent - it inserts fixed ids so the
  sample rows stay recognisable, and guards against a second run rather than
  silently double-loading.
