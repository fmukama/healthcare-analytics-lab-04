 ETL DESIGN - OLTP to Star Schema
 Part 3.4
*******************************************************

The ETL is where a star schema stops being a diagram and starts being faster.
Nothing in fact_encounters can be SELECTed out of the OLTP database -
is_readmit_30d, total_allowed_amount and diagnosis_count do not exist there. This
load computes them once, off-hours, so no analyst pays for them again.

Three files, run in order by `make etl`:
    sql/etl/01_dims.sql      dimensions
    sql/etl/02_fact.sql      fact_encounters
    sql/etl/03_bridges.sql   both bridges

Measured: ~16 seconds for 70,004 fact rows, 175,024 diagnosis bridge rows and
104,955 procedure bridge rows.


------------------------------------------------------------------------------
LOAD ORDER
------------------------------------------------------------------------------
    1. dim_date                one-time, generated, not extracted
    2. Unknown members         key = -1 in every dimension
    3. Independent dimensions  specialty, department, patient, encounter type,
                               diagnosis, procedure
    4. dim_provider            needs specialty_key and department_key
    5. fact_encounters         needs every dimension key
    6. Bridges                 need encounter_sk from the fact

  Teardown reverses it. Getting this wrong makes the foreign keys reject the load,
  which is what foreign keys are for - a load that fails is strictly better than
  one that half-succeeds.


------------------------------------------------------------------------------
1. DIMENSION LOAD
------------------------------------------------------------------------------
  Upsert, never truncate-and-reload: INSERT ... ON CONFLICT (natural_key) DO UPDATE.

  The reason is surrogate key stability. The fact stores patient_key, not
  patient_id. Truncating dim_patient and reloading would reassign those keys, and
  every existing fact row would silently point at a different patient. Nothing
  errors; every report is wrong. Conflicting on the natural key means the surrogate
  assigned on the first load survives forever - and makes the step idempotent by
  construction. Verified: re-running the ETL leaves all counts and all money
  identical.

  SCD Type 1 (overwrite). No question here asks "what was true at the time".
  Cost: a patient who changes surname reprints under the new name in last year's
  report. Type 2 would mean valid_from / valid_to / is_current and a unique key of
  (patient_id, valid_from) - sketched in the DDL, not built.

  dim_date is generated, not extracted, covering 2023-2027 so a late-arriving fact
  always finds a date row. A missing date row would reject the fact load.

  Unknown members first, so a failed lookup still produces a valid NOT NULL foreign
  key. dim_provider's Unknown row comes after the specialty and department Unknowns,
  because its own foreign keys must resolve to something.

  dim_encounter_type is a curated VALUES list, not SELECT DISTINCT off encounters -
  deriving reference data from facts means 'ER' disappears in any period with no ER
  visits.

  dim_provider loads last, with LEFT JOIN + COALESCE(key, -1). A provider with a
  broken department_id must still load: dropping the provider row here would later
  drop every one of their encounters from the fact.


------------------------------------------------------------------------------
2. FACT LOAD
------------------------------------------------------------------------------
  Three techniques, each preventing a specific silent bug.

  TECHNIQUE 1 - aggregate the many-side first, in separate CTEs.
  diagnosis_count, procedure_count and the billing measures are each computed in
  their own CTE returning one row per encounter, and only then LEFT JOINed. Joining
  encounter_diagnoses and billing directly onto encounters and aggregating
  afterwards is the fan trap: total_allowed_amount would be multiplied by
  diagnosis_count, roughly 2.5x here. Aggregate first, join second.
      Verified: SUM(diagnosis_count) = 175,024 = COUNT(encounter_diagnoses)
                SUM(total_allowed_amount) = $139,591,191.31, matching billing to
                the cent.

  TECHNIQUE 2 - compute the readmission flag once.
  A LATERAL finds the earliest subsequent encounter for the same patient;
  is_readmit_30d is set when that date falls within 30 days of discharge on an
  inpatient stay.

  Chosen over LEAD(encounter_date) OVER (PARTITION BY patient_id ...). LEAD is
  cheaper but wrong at the edges: it inspects only the immediately next encounter,
  so an overlapping stay beginning before discharge masks a later qualifying return.
      Verified against the honest self-join, per specialty, all 8 matching -
      8,493 index stays and 2,765 readmissions either way.

  The lateral needs an index on (patient_id, encounter_date) to be affordable;
  without one this is the same scan-per-row that makes Q3 cost 8.7s and 8.9M buffer
  reads. The load builds a TEMP copy of encounters and indexes that, rather than
  indexing public.encounters, for two reasons: it does not touch the source system,
  and it cannot be left behind. An index accidentally left on public.encounters
  would make a later Q3 run fast and silently invalidate the whole comparison. Temp
  objects drop at session end even if the script fails.

  That trade is the thesis in miniature: the warehouse can afford an index the
  transactional system deliberately does not carry, because it pays for it once, at
  night, instead of on every insert.

  TECHNIQUE 3 - LEFT JOIN every dimension, COALESCE the key to -1.
  An INNER JOIN would silently drop any encounter whose dimension lookup failed.
  Dropping facts is the worst failure mode available: the numbers come out wrong and
  nothing raises an error. LEFT + COALESCE keeps the row and makes the defect
  countable with one query.
      Verified: 70,004 fact rows for 70,004 encounters, 0 resolving to Unknown.

  Missing data policy. Unbilled gets 0, not NULL - additive measures, and 0 is the
  truthful identity, whereas NULL would make AVG() skip the row. claim_count is the
  discriminator: 13,430 rows have claim_count = 0, being 8,406 never billed plus
  5,024 wholly denied. days_to_next_encounter is the one column where NULL is
  correct, because "no subsequent visit" is a real answer, not a failed lookup.

  The Denied-claim filter in the billing CTE must match Q4's WHERE clause exactly.
  If they diverge the parity test fails - and the ETL is what is wrong, not the test.

  Grain is enforced by the database, not by hope. A UNIQUE constraint on
  encounter_id means an ETL bug that fans rows out fails loudly at load time instead
  of quietly doubling every number downstream.

  Re-runs are upserts, and every measure appears in the DO UPDATE list. A column
  omitted there is a bug that appears only on the SECOND load, as a stale number
  nobody is looking for.


------------------------------------------------------------------------------
3. BRIDGE LOAD
------------------------------------------------------------------------------
  Runs after the fact, because both bridges need encounter_sk.

  These use INNER JOIN where the fact load used LEFT JOIN everywhere. Not an
  inconsistency - a difference in what a missing parent means. A fact row with an
  unresolvable patient is still a real encounter worth counting, so it loads with
  patient_key = -1. A bridge row pointing at an encounter that does not exist is not
  a partial record, it is garbage, and it should be dropped.

  bridge_encounter_diagnoses conflicts on (encounter_sk, diagnosis_key), so a
  repeated ICD-10 code within one encounter collapses - correct, because the same
  diagnosis twice for one visit is a data entry error.

  bridge_encounter_procedures conflicts on the source's own encounter_procedure_id
  instead. The same CPT code can legitimately occur twice - two chest X-rays are two
  billable events - so a composite key would swallow the second and procedure_count
  would stop matching the bridge. Conflicting on the source row's identity preserves
  every occurrence and stays idempotent.
      Verified: bridge rows equal the fact's stored counts exactly, 175,024 and
      104,955, with 0 orphans.


------------------------------------------------------------------------------
4. REFRESH STRATEGY
------------------------------------------------------------------------------
  Cadence. Nightly batch, after the OLTP day closes. Analytics does not need
  real-time data, and batch is cheaper to reason about than streaming.

  Full versus incremental. Dimensions are small, so a full upsert every night is
  fine and avoids change-detection logic entirely. The fact is large and should load
  incrementally, filtered on encounter_date >= (last load - 7 days) so recent
  corrections are picked up.

  Late-arriving facts. Billing lands days after the encounter, so
  total_allowed_amount changes after the fact row exists. This is why the fact load
  is an upsert rather than an insert, and why the lookback window exists: an
  encounter loaded Monday with total_allowed_amount = 0 gets corrected on Thursday
  when the claim posts.

  Late-arriving dimensions. A fact referencing a patient not yet in dim_patient can
  either point at -1 and be re-resolved next run, or get an inferred member - a
  dimension row carrying only the natural key, attributes filled in when the real
  record arrives. I would use the inferred member in production, because -1 loses
  the link between the fact and the patient it belongs to.

  The readmission recompute window - the subtle one. is_readmit_30d depends on the
  NEXT encounter, which may not exist when the row is first loaded. A stay
  discharged Monday only becomes a readmission when the return arrives, possibly
  weeks later. So an incremental load cannot only process new rows: it must
  recompute already-loaded rows at least 30 days back, and I would use 45 for
  safety. A direct and easily missed consequence of pre-computing anything that
  depends on the future.

  Idempotency. Every statement in all three files is ON CONFLICT, so a re-run
  changes nothing. Verified by running the full ETL twice and comparing row counts
  and total revenue - identical.

  Watermark. Store last_loaded_at in a small audit table so incremental runs know
  where to resume, rather than inferring it from max(load_ts) on the fact.

  Failure handling. Each step runs under ON_ERROR_STOP so a failure aborts rather
  than continuing with a half-loaded table. In production each step would be wrapped
  in its own transaction: a stale warehouse is recoverable, a half-loaded one quietly
  reports wrong numbers to the business.
