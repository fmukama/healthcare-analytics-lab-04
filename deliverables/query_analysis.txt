QUESTION 1: Monthly encounters by specialty and encounter type
------------------------------------------------------------------------------

SQL Query:
-- Q1: Monthly encounters by specialty and encounter type.
-- Joins: encounters -> providers -> specialties   (3 tables, 2 joins)
SELECT
    date_trunc('month', e.encounter_date)::date AS month,
    s.specialty_name,
    e.encounter_type,
    COUNT(*)                        AS total_encounters,
    COUNT(DISTINCT e.patient_id)    AS unique_patients
FROM encounters e
JOIN providers   p ON p.provider_id  = e.provider_id
JOIN specialties s ON s.specialty_id = p.specialty_id
GROUP BY 1, 2, 3
ORDER BY 1, 2, 3

Schema Analysis:
  - Tables joined   : encounters, providers, specialties
  - Number of joins : 2 (both INNER, and CHAINED - specialties is only reachable
                      through providers)
  - Rows scanned    : 70,075  (70,004 encounters + 63 providers + 8 specialties)
  - Rows aggregated : 70,004 -> 576 output rows

Bottleneck Identified:
  Four separate costs, and only the first is the one people name.

  1. An encounter does not know its own specialty. The label lives two hops away
     (encounters -> providers -> specialties), so all 70,004 rows are pushed
     through two joins just to attach one word. The joins themselves are cheap -
     the plan hashes both small dimensions - but the chain is unavoidable.

  2. The full table is read every time. There is no filter, so idx_encounter_date
     is correctly ignored and the plan does a Seq Scan. An index helps you find a
     few rows; this query wants all of them.

  3. GROUP BY derives the month with date_trunc() per row - a function call on
     every one of the 70,004 rows to produce 24 distinct values.

  4. The real cost: COUNT(DISTINCT patient_id) cannot use a running counter, so
     Postgres falls back to a GroupAggregate and must SORT all 70,004 rows on
     four keys, including patient_id. The plan shows quicksort using 6,875 kB,
     and the sort node runs from 108ms to 114ms of a ~122ms query - the single
     dominant cost.

  The shape of the waste: 70,004 rows sorted to produce 576. Everything expensive
  here is recomputed identically on every single run.

Performance (measured):

  - Final run reported    : 121.250 ms
  - Buffers: shared hit=653

QUESTION 2: Top diagnosis-procedure pairs
------------------------------------------------------------------------------

SQL Query:
-- Q2: Top diagnosis-procedure pairs.
-- Joins: encounter_diagnoses -> diagnoses, encounter_procedures -> procedures,
-- both hanging off encounters via encounter_id (4 tables, 3 joins).
--
-- Row explosion: joining two many-to-many tables to the same encounter builds
-- a cross product per encounter (2 dx x 2 px -> 4 rows before GROUP BY). So
-- COUNT(*) over the whole join is NOT "how many encounters". Once grouped
-- down to one (icd10_code, cpt_code) pair though, an encounter contributes at
-- most one row per pair here (no encounter repeats a dx or px code -- see
-- 03_volume.sql's step-by-coprime-number generation). We still write
-- COUNT(DISTINCT ed.encounter_id), not COUNT(*): it means "encounters with
-- this pair" by definition, and doesn't quietly break if that no-duplicates
-- guarantee ever stops holding.
--
-- INNER JOIN to encounter_procedures is deliberate: an encounter with zero
-- procedures has no diagnosis-procedure PAIR to contribute, so dropping it
-- here is correct -- unlike Q4, this isn't a missing-data problem.
SELECT
    d.icd10_code,
    d.icd10_description,
    pr.cpt_code,
    pr.cpt_description,
    COUNT(DISTINCT ed.encounter_id) AS encounter_count
FROM encounter_diagnoses  ed
JOIN diagnoses            d  ON d.diagnosis_id  = ed.diagnosis_id
JOIN encounter_procedures ep ON ep.encounter_id = ed.encounter_id
JOIN procedures           pr ON pr.procedure_id = ep.procedure_id
GROUP BY 1, 2, 3, 4
ORDER BY encounter_count DESC
LIMIT 20


Schema Analysis:
  - Tables joined   : encounter_diagnoses, diagnoses, encounter_procedures,
                      procedures
  - Number of joins : 3 (all INNER)
  - Rows scanned    : 280,079  (175,024 dx + 104,955 px + 60 + 40)
  - Intermediate    : 262,323 rows materialised BEFORE aggregation
  - Rows aggregated : 262,323 -> 2,400 groups -> top 20

Bottleneck Identified:
  Row explosion from joining two many-to-many tables to the same parent.

  Each encounter carries ~2.5 diagnoses and ~1.5 procedures. Joining both
  junction tables on encounter_id produces their CROSS PRODUCT per encounter, so
  an encounter with 2 diagnoses and 2 procedures contributes 4 rows, not 2.
  Measured independently of the plan:

      SELECT sum(dx.c * px.c) ...  =  262,323

  and the plan's join node reports exactly 262,323 actual rows, so 70,004
  encounters inflate to 262,323 intermediate rows - 3.75x - before a single group
  is formed. That intermediate set is then sorted (quicksort, 30 MB) to feed a
  GroupAggregate, and the aggregate node alone accounts for ~1,340ms of the
  ~1,455ms total.

  The correctness consequence matters more than the speed. Because rows are
  duplicated, COUNT(*) does NOT mean "number of encounters" - it counts
  (diagnosis x procedure) pairings. The query uses COUNT(DISTINCT ed.encounter_id)
  for that reason, which is right but forces the sort that makes it slow.

  Two deliberate choices worth recording:
  - INNER join to encounter_procedures. The 11,725 encounters with no procedure
    (16.7%) are dropped, and that is correct here: an encounter with no procedure
    has no diagnosis-procedure PAIR to contribute. This is not the missing-data
    problem Q4 has.
  - No tiebreaker on ORDER BY encounter_count DESC. With LIMIT 20 and 8 pairs
    tied at the cut value of 140 for 7 remaining slots, the top-20 is genuinely
    not unique - see notes on SQ2.

QUESTION 3: 30-day readmission rate by specialty
------------------------------------------------------------------------------

SQL Query:
-- Q3: 30-day readmission rate by specialty.
-- Chain: encounters self-joined (via EXISTS) on patient_id, plus providers ->
-- specialties for the index stay.
--
-- Definition: an INDEX STAY is an Inpatient encounter. It is a readmission if
-- the SAME patient has any later encounter starting after discharge_date and
-- within 30 days of it.
--
-- Trap A: a patient can return more than once in 30 days -- a plain JOIN would
-- count that index stay multiple times, pushing the rate over 100%. EXISTS
-- flags each index stay at most once, avoiding that.
-- Trap B: specialty is the INDEX stay's (the care being judged), not the
-- returning visit's.
-- Trap C: strictly `>` discharge_date, not `>=` -- a same-day transfer is not
-- treated as a readmission.
WITH index_stays AS (
    SELECT e.encounter_id, e.patient_id, e.discharge_date, p.specialty_id
    FROM encounters e
    JOIN providers p ON p.provider_id = e.provider_id
    WHERE e.encounter_type = 'Inpatient'
      AND e.discharge_date IS NOT NULL
),
flagged AS (
    SELECT
        i.*,
        EXISTS (
            SELECT 1 FROM encounters e2
            WHERE e2.patient_id = i.patient_id
              AND e2.encounter_id <> i.encounter_id
              AND e2.encounter_date >  i.discharge_date
              AND e2.encounter_date <= i.discharge_date + INTERVAL '30 days'
        ) AS is_readmit
    FROM index_stays i
)
SELECT
    s.specialty_name,
    COUNT(*)                                        AS index_stays,
    SUM(CASE WHEN f.is_readmit THEN 1 ELSE 0 END)   AS readmissions,
    ROUND(100.0 * SUM(CASE WHEN f.is_readmit THEN 1 ELSE 0 END)
                / NULLIF(COUNT(*), 0), 2)            AS readmission_rate_pct
FROM flagged f
JOIN specialties s ON s.specialty_id = f.specialty_id
GROUP BY 1
ORDER BY readmission_rate_pct DESC


Schema Analysis:
  - Tables joined   : encounters (twice - self-referencing), providers,
                      specialties
  - Number of joins : 2 explicit INNER joins, plus a CORRELATED SUBQUERY that
                      re-reads encounters once per index stay
  - Rows scanned    : 8,493 index stays, but the subquery re-scans encounters
                      for each one
  - Buffers touched : 8,939,200
  - Rows aggregated : 8,493 -> 8 output rows

Bottleneck Identified:
  This is the slowest query in the lab by two orders of magnitude, and the
  timing alone hides why. The buffer count is where the story is.

  8,939,200 buffer hits, at 8 kB per page, is roughly 71 GB of logical reads to
  produce 8 rows. Compare Q1's 653 buffers for the same underlying table. The
  cause is the correlated EXISTS: for each of the 8,493 inpatient index stays,
  Postgres re-scans encounters looking for a later visit by the same patient.
  8,493 x ~640 pages per scan is ~5.4M, and the plan reports 8.9M once the
  aggregate's overhead is included.

  The plan shows the split cleanly: the joins and the index-stay scan finish in
  well under a second; the GroupAggregate node then runs from 1,269ms to
  9,380ms. Roughly 8.1 seconds - about 92% of the query - is spent evaluating
  the SubPlan.

  Two structural reasons it cannot be fast in this schema:

  1. There is no index on encounters.patient_id. Foreign keys do not create one
     in Postgres, and 01_schema.sql deliberately does not add one, because that
     is the honest OLTP shape - the transactional system has no reason to carry
     an index that only analytics needs.

  2. Even with one, the match is a RANGE condition on dates
     (encounter_date > discharge_date AND <= discharge_date + 30 days). Ranges
     cannot be hashed, so the planner cannot turn this into a cheap hash
     semi-join the way it does for Q1's equality joins.

  The cost also scales quadratically. Measured across dataset sizes: 7,000
  encounters -> 83ms; 30,000 -> 1,412ms; 60,000 -> 5,556ms; 600,000 -> over
  265,000ms. Doubling the data roughly quadruples the time, which means this
  query does not merely run slowly today - it stops being viable at all as the
  hospital's history grows.

  Correctness notes (both deliberate):
  - EXISTS rather than a JOIN. A patient returning twice within 30 days would be
    counted twice by a naive join, producing rates above 100%. EXISTS flags each
    index stay at most once.
  - The specialty attributed is the INDEX stay's provider, not the returning
    visit's, because the index stay is the care being judged.
  - Strictly `>` discharge_date, so a same-day transfer is not a readmission.

QUESTION 4: Revenue by specialty and month
------------------------------------------------------------------------------

SQL Query:
-- Q4: Revenue by specialty and month.
-- Chain: billing -> encounters -> providers -> specialties (4 tables, 3 joins),
-- exactly as the assignment names it.
--
-- Decision (a) date: encounter_date, not billing.claim_date -- revenue lines
-- up with when the care happened, not when the claim was filed weeks later.
-- Decision (b) amount: allowed_amount (what the insurer agreed to pay), not
-- claim_amount (what the hospital asked for).
-- Decision (c) 'Denied' claims are excluded -- the insurer isn't paying
-- allowed_amount on those, so counting them overstates revenue. 'Pending' is
-- kept: allowed_amount is the contractually agreed figure, so it's legitimate
-- expected revenue even before cash is actually collected.
-- Decision (d) INNER JOIN billing -> encounters, not LEFT: this query is
-- anchored on billing by definition (it's a revenue question) -- an encounter
-- that was never billed has no allowed_amount to sum, so starting FROM
-- billing loses nothing here. (LEFT JOIN + COALESCE(...,0) would matter for a
-- different metric, e.g. "average revenue per encounter" -- not this one.)
SELECT
    date_trunc('month', e.encounter_date)::date AS month,
    s.specialty_name,
    SUM(b.allowed_amount) AS total_allowed,
    COUNT(*)              AS claim_count
FROM billing b
JOIN encounters  e ON e.encounter_id = b.encounter_id
JOIN providers   p ON p.provider_id  = e.provider_id
JOIN specialties s ON s.specialty_id = p.specialty_id
WHERE b.claim_status <> 'Denied'
GROUP BY 1, 2
ORDER BY total_allowed DESC


Schema Analysis:
  - Tables joined   : billing, encounters, providers, specialties
  - Number of joins : 3 (all INNER) - the longest chain in the lab, exactly the
                      billing -> encounters -> providers -> specialties path the
                      brief names
  - Rows scanned    : 126,649  (56,574 billing rows surviving the filter, from
                      61,598, + 70,004 encounters + 63 + 8)
  - Rows aggregated : 56,574 -> 192 output rows

Bottleneck Identified:
  The same disease as Q1, one hop worse, but the mildest case in the lab.

  Revenue lives in billing, the month lives on encounters, and the specialty is
  two further hops away through providers. Nothing in the schema lets a claim
  know which specialty earned it, so the whole chain must be walked to attach one
  label to each of 56,574 rows. The plan builds a 70,004-row hash of encounters
  and streams billing past it, then hashes the two small dimensions.

  It is only ~93ms because the aggregation is a HashAggregate rather than the
  sort Q1 needs - SUM and COUNT can both run with a running accumulator, so
  nothing has to be ordered. That is the useful contrast with Q1: same shape,
  one more join, but no COUNT(DISTINCT), and it comes out twice as fast.

  What makes it slow is therefore not the aggregate but the join chain plus
  re-deriving date_trunc('month', ...) on every surviving row, all of it
  recomputed from scratch on every run.

  Four decisions this query forced, all recorded in design_decisions.txt:
  a) Month comes from encounter_date, not claim_date, so revenue lines up with
     when care was delivered rather than when paperwork was filed weeks later.
  b) allowed_amount (what the insurer agreed to pay), not claim_amount (what was
     asked for). The brief asks for allowed.
  c) Denied claims are excluded - 5,024 of 61,598. Counting them overstates
     revenue at $151.8M against a truthful $139.6M. Pending claims are kept,
     because allowed_amount is the contractually agreed figure.
  d) The query is anchored FROM billing, so the 8,406 unbilled encounters simply
     do not appear. That is right for a revenue question - there is no
     allowed_amount to sum. It would be wrong for "average revenue per
     encounter", which is a different question needing a LEFT JOIN and COALESCE.

  - Final run reported    : 46.055 ms
  - Buffers: shared hit=1161
