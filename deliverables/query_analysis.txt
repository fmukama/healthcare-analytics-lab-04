QUESTION 1: Monthly encounters by specialty and encounter type
------------------------------------------------------------------------------

SQL Query:
-- Q1: Monthly encounters by specialty and encounter type.
-- Joins: encounters -> providers -> specialties   (3 tables, 2 joins)
SELECT
    date_trunc('month', e.encounter_date)::date AS month,
    s.specialty_name,
    e.encounter_type,
    COUNT(*)                        AS total_encounters,
    COUNT(DISTINCT e.patient_id)    AS unique_patients
FROM encounters e
JOIN providers   p ON p.provider_id  = e.provider_id
JOIN specialties s ON s.specialty_id = p.specialty_id
GROUP BY 1, 2, 3
ORDER BY 1, 2, 3

Schema Analysis:
  - Tables joined   : encounters, providers, specialties
  - Number of joins : 2 INNER, chained - specialties is only reachable via providers
  - Rows scanned    : 70,075  (70,004 encounters + 63 providers + 8 specialties)
  - Rows aggregated : 70,004 -> 576 output rows

Bottleneck Identified:
  The sort, not the joins.

  COUNT(DISTINCT patient_id) has no running-counter form, so the planner uses a
  GroupAggregate and sorts all 70,004 rows (quicksort, 6,875 kB). That sort
  dominates. The joins are cheap - both dimensions hash.

  Three costs behind it:
  1. An encounter does not know its own specialty. Every row walks
     encounters -> providers -> specialties to attach one word.
  2. No filter, so the plan correctly ignores idx_encounter_date and does a Seq
     Scan. An index finds a few rows; this query wants all of them.
  3. date_trunc() runs per row - 70,004 calls to produce 24 months.

  70,004 rows sorted to return 576, recomputed identically every run.

Performance (measured):
  - Median execution time : 101.355 ms   (1 discarded warm-up, median of 3)
  - Final run reported    : 100.610 ms
  - Buffers: shared hit=653

QUESTION 2: Top diagnosis-procedure pairs
------------------------------------------------------------------------------

SQL Query:
-- Q2: Top diagnosis-procedure pairs.
-- Joins: encounter_diagnoses -> diagnoses, encounter_procedures -> procedures,
-- both hanging off encounters via encounter_id (4 tables, 3 joins).
--
-- Row explosion: joining two many-to-many tables to the same encounter builds
-- a cross product per encounter (2 dx x 2 px -> 4 rows before GROUP BY). So
-- COUNT(*) over the whole join is NOT "how many encounters". Once grouped
-- down to one (icd10_code, cpt_code) pair though, an encounter contributes at
-- most one row per pair here (no encounter repeats a dx or px code -- see
-- 03_volume.sql's step-by-coprime-number generation). We still write
-- COUNT(DISTINCT ed.encounter_id), not COUNT(*): it means "encounters with
-- this pair" by definition, and doesn't quietly break if that no-duplicates
-- guarantee ever stops holding.
--
-- INNER JOIN to encounter_procedures is deliberate: an encounter with zero
-- procedures has no diagnosis-procedure PAIR to contribute, so dropping it
-- here is correct -- unlike Q4, this isn't a missing-data problem.
SELECT
    d.icd10_code,
    d.icd10_description,
    pr.cpt_code,
    pr.cpt_description,
    COUNT(DISTINCT ed.encounter_id) AS encounter_count
FROM encounter_diagnoses  ed
JOIN diagnoses            d  ON d.diagnosis_id  = ed.diagnosis_id
JOIN encounter_procedures ep ON ep.encounter_id = ed.encounter_id
JOIN procedures           pr ON pr.procedure_id = ep.procedure_id
GROUP BY 1, 2, 3, 4
ORDER BY encounter_count DESC
LIMIT 20


Schema Analysis:
  - Tables joined   : encounter_diagnoses, diagnoses, encounter_procedures,
                      procedures
  - Number of joins : 3 (all INNER)
  - Rows scanned    : 280,079  (175,024 dx + 104,955 px + 60 + 40)
  - Intermediate    : 262,323 rows materialised BEFORE aggregation
  - Rows aggregated : 262,323 -> 2,400 groups -> top 20

Bottleneck Identified:
  Row explosion from joining two many-to-many tables to the same parent.

  Each encounter has ~2.5 diagnoses and ~1.5 procedures. Joining both junction
  tables on encounter_id yields their CROSS PRODUCT per encounter, so 70,004
  encounters inflate to 262,323 rows - 3.75x - before a single group forms.
  Verified independently: SUM(dx.c * px.c) = 262,323, exactly what the plan
  reports. That set is then sorted (quicksort, 30 MB) to feed a GroupAggregate.

  The correctness consequence matters more than the speed: because rows are
  duplicated, COUNT(*) counts (diagnosis x procedure) pairings, not encounters.
  The query uses COUNT(DISTINCT ed.encounter_id) - right, and it forces the sort.

  Two deliberate choices:
  - INNER join to encounter_procedures drops the 11,725 encounters with no
    procedure (16.7%), correctly: no procedure means no dx-px pair to contribute.
  - No ORDER BY tiebreaker, so the top-20 is genuinely not unique. See SQ2.

QUESTION 3: 30-day readmission rate by specialty
------------------------------------------------------------------------------

SQL Query:
-- Q3: 30-day readmission rate by specialty.
-- Chain: encounters self-joined (via EXISTS) on patient_id, plus providers ->
-- specialties for the index stay.
--
-- Definition: an INDEX STAY is an Inpatient encounter. It is a readmission if
-- the SAME patient has any later encounter starting after discharge_date and
-- within 30 days of it.
--
-- Trap A: a patient can return more than once in 30 days -- a plain JOIN would
-- count that index stay multiple times, pushing the rate over 100%. EXISTS
-- flags each index stay at most once, avoiding that.
-- Trap B: specialty is the INDEX stay's (the care being judged), not the
-- returning visit's.
-- Trap C: strictly `>` discharge_date, not `>=` -- a same-day transfer is not
-- treated as a readmission.
WITH index_stays AS (
    SELECT e.encounter_id, e.patient_id, e.discharge_date, p.specialty_id
    FROM encounters e
    JOIN providers p ON p.provider_id = e.provider_id
    WHERE e.encounter_type = 'Inpatient'
      AND e.discharge_date IS NOT NULL
),
flagged AS (
    SELECT
        i.*,
        EXISTS (
            SELECT 1 FROM encounters e2
            WHERE e2.patient_id = i.patient_id
              AND e2.encounter_id <> i.encounter_id
              AND e2.encounter_date >  i.discharge_date
              AND e2.encounter_date <= i.discharge_date + INTERVAL '30 days'
        ) AS is_readmit
    FROM index_stays i
)
SELECT
    s.specialty_name,
    COUNT(*)                                        AS index_stays,
    SUM(CASE WHEN f.is_readmit THEN 1 ELSE 0 END)   AS readmissions,
    ROUND(100.0 * SUM(CASE WHEN f.is_readmit THEN 1 ELSE 0 END)
                / NULLIF(COUNT(*), 0), 2)            AS readmission_rate_pct
FROM flagged f
JOIN specialties s ON s.specialty_id = f.specialty_id
GROUP BY 1
ORDER BY readmission_rate_pct DESC


Schema Analysis:
  - Tables joined   : encounters (twice - self-referencing), providers, specialties
  - Number of joins : 2 INNER, plus a CORRELATED SUBQUERY that re-reads encounters
                      once per index stay
  - Rows scanned    : 8,493 index stays, each triggering a re-scan of encounters
  - Buffers touched : 8,939,200
  - Rows aggregated : 8,493 -> 8 output rows

Bottleneck Identified:
  The slowest query by two orders of magnitude. The timing hides why; the buffer
  count is the story.

  8,939,200 buffer hits at 8 kB per page is ~71 GB of logical reads to produce 8
  rows. Q1 touches 653 buffers against the same table. Cause: the correlated
  EXISTS re-scans encounters for each of the 8,493 inpatient index stays, looking
  for a later visit by the same patient.

  Two structural reasons it cannot be fast here:
  1. No index on encounters.patient_id. Foreign keys do not create one, and
     01_schema.sql deliberately does not add one - a transactional system has no
     reason to carry an index only analytics needs.
  2. The match is a date RANGE (> discharge_date AND <= +30 days). Ranges cannot be
     hashed, so the planner cannot use a cheap hash semi-join.

  It scales quadratically: 7,000 encounters -> 83ms; 30,000 -> 1,412ms; 60,000 ->
  5,556ms; 600,000 -> over 265,000ms. It does not merely run slowly today - it
  stops being viable as history grows.

  Correctness notes, all deliberate: EXISTS not JOIN (a patient returning twice in
  30 days would be counted twice, pushing the rate over 100%); the specialty is the
  INDEX stay's, since that is the care being judged; strictly > discharge_date, so
  a same-day transfer is not a readmission.

QUESTION 4: Revenue by specialty and month
------------------------------------------------------------------------------

SQL Query:
-- Q4: Revenue by specialty and month.
-- Chain: billing -> encounters -> providers -> specialties (4 tables, 3 joins),
-- exactly as the assignment names it.
--
-- Decision (a) date: encounter_date, not billing.claim_date -- revenue lines
-- up with when the care happened, not when the claim was filed weeks later.
-- Decision (b) amount: allowed_amount (what the insurer agreed to pay), not
-- claim_amount (what the hospital asked for).
-- Decision (c) 'Denied' claims are excluded -- the insurer isn't paying
-- allowed_amount on those, so counting them overstates revenue. 'Pending' is
-- kept: allowed_amount is the contractually agreed figure, so it's legitimate
-- expected revenue even before cash is actually collected.
-- Decision (d) INNER JOIN billing -> encounters, not LEFT: this query is
-- anchored on billing by definition (it's a revenue question) -- an encounter
-- that was never billed has no allowed_amount to sum, so starting FROM
-- billing loses nothing here. (LEFT JOIN + COALESCE(...,0) would matter for a
-- different metric, e.g. "average revenue per encounter" -- not this one.)
SELECT
    date_trunc('month', e.encounter_date)::date AS month,
    s.specialty_name,
    SUM(b.allowed_amount) AS total_allowed,
    COUNT(*)              AS claim_count
FROM billing b
JOIN encounters  e ON e.encounter_id = b.encounter_id
JOIN providers   p ON p.provider_id  = e.provider_id
JOIN specialties s ON s.specialty_id = p.specialty_id
WHERE b.claim_status <> 'Denied'
GROUP BY 1, 2
ORDER BY total_allowed DESC


Schema Analysis:
  - Tables joined   : billing, encounters, providers, specialties
  - Number of joins : 3 (all INNER) - the longest chain in the lab, exactly the
                      billing -> encounters -> providers -> specialties path
  - Rows scanned    : 126,649  (56,574 billing rows surviving the filter, of
                      61,598, + 70,004 encounters + 63 + 8)
  - Rows aggregated : 56,574 -> 192 output rows

Bottleneck Identified:
  The same disease as Q1, one hop worse - but the mildest case in the lab.

  Revenue lives in billing, the month on encounters, the specialty two further hops
  through providers. Nothing lets a claim know which specialty earned it, so the
  whole chain is walked to attach one label to each of 56,574 rows.

  It stays under 60ms because the aggregation is a HashAggregate, not the sort Q1
  needs - SUM and COUNT run with a running accumulator, so nothing is ordered. That
  is the contrast with Q1: one more join, no COUNT(DISTINCT), and it is faster.

  So the cost is the join chain plus re-deriving date_trunc('month', ...) per
  surviving row, recomputed from scratch every run.

  Four decisions this query forced (see design_decisions.txt):
  a) Month from encounter_date, not claim_date - revenue lines up with when care
     was delivered, not when paperwork was filed.
  b) allowed_amount (what the insurer agreed to pay), not claim_amount.
  c) Denied claims excluded - 5,024 of 61,598. Counting them overstates revenue at
     $151.8M against a truthful $139.6M. Pending is kept: allowed_amount is
     contractually agreed.
  d) Anchored FROM billing, so unbilled encounters do not appear. Correct for a
     revenue question; wrong for "average revenue per encounter", which needs a
     LEFT JOIN and COALESCE.
